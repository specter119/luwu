# M5: Batch Performance and Interruption Safety

Status: closed on 2026-09-22. This record owns the bounded delivery scope and
dated closure evidence. Delivery order belongs to [roadmap](../roadmap.md);
existing public behavior remains owned by [reference](../reference.md).

## Motivation: isolated pilot on 2026-09-20

The installed Luwu 0.1.0 package matched source checkout
`20bcae2b86140298c6a40e1d7b507e82e061a09d`. The local dotfiles snapshot was
`d4735b4dbe860cd0857086a3836f7a5b260b232c`; remote freshness was not checked.
The experiment ran in a networkless Bubblewrap namespace with synthetic HOME,
without real local inputs, credentials, hooks or production deployment.

- The representative public pilot passed 37 checks, including expected
  refusals. Three real-file samples completed apply, unchanged reapply and
  recovery observation. Pi reverse sync used a reduced public JSON model.
- Global static expansion planned 176 candidates with no blocked resources;
  it was not the current machine's selected package closure.
- Full batch apply was interrupted at approximately 150 seconds. Its journal
  contained 17 committed, one commit-intent and 158 preflighted resources.
  Read-only recovery reported recovery required, with 17 confirmed and 159
  changed-or-unknown observations. Full deployment and reapply did not complete.
- The fake-provider probe passed its narrow boundary checks. Real rbw and
  platform integration were not tested. A separate current-source run passed
  59 targeted unit tests; neither result is an M5 gate.

Temporary supporting artifacts were under
`/tmp/luwu-dotfiles-eval.VUPNSR/`: `public-run-hlto_03w/results.json`,
`dotfiles/luwu-pilot/run.py`, `dotfiles/luwu-pilot/README.md`, and
`dotfiles/luwu-pilot/interrupted-{record-inspect,recovery}.json`.
These paths may expire. Preserve or reconstruct sanitized fixtures and the
benchmark harness in the repository during M5; closure must not depend on
temporary files or access to the original user's HOME.

The reviewed source has repeated full-manifest loading inside per-resource
write preflight, pairwise resource-path validation, and repeated whole-journal
history/provenance validation and publication. These paths produce cubic
aggregate work in a batch. Journal synchronization adds filesystem costs.
This identifies credible optimization targets, not measured attribution:
profile CPU, allocation, serialization and filesystem time before choosing
the implementation. Do not extrapolate the interrupted run into full latency.

## Delivery slices

1. **M5a — baseline and profiling.** Add a sanitized reproducible fixture and
   command-level benchmark. Measure 1, 10, 30, 100, 176 and 200 resources for
   plan, fresh apply, one-change apply, all-changed apply, no-op apply and
   recovery. Use literal-file links and a small mixed public template set;
   measure provider latency separately with synthetic inputs.
1. **M5b — validation cost.** Remove repeated global structural work while
   retaining fresh manifest/source/target identity and alias validation at
   the required write boundaries. Prove invalidation on mutations; an
   unchecked cached plan is not an optimization.
1. **M5c — journal cost.** Reduce redundant full-history validation, copying
   and publication without changing what is durable before or after a target
   replacement. Keep record compatibility, CAS, corruption rejection and
   metadata-only persistence. If a storage-contract change is necessary,
   resolve its version/migration design before implementing it.
1. **M5d — acceptance.** Run installed-artifact benchmarks, fault injection and
   the existing boundary/release gates. Preserve raw timing data and a closure
   report with before/after measurements and explicit limitations.

These are slices within one milestone, not four additional milestones. Avoid
parallel writers as the first optimization: concurrency must not obscure the
existing ordering and partial-success boundaries.

## Initial performance acceptance budgets

These are development targets, not measured results or universal CLI promises.
Use the same recorded Linux host, local durable filesystem, Python version,
fixture and sandbox mode for before/after comparisons. Exclude setup from
timing; include process startup, preflight, journal writes, target durability
and verification in the measured command. Do not use tmpfs for acceptance.

For 200 public resources, the initial warm-run median budgets are:

| Operation                  | Budget             |
| -------------------------- | ------------------ |
| Plan                       | At most 1 second   |
| No-op apply                | At most 2 seconds  |
| One-change apply           | At most 3 seconds  |
| Fresh or all-changed apply | At most 10 seconds |
| Read-only recovery         | At most 2 seconds  |

Run at least five repetitions for each scenario, reporting every sample,
median and maximum; warm maxima should not exceed twice the corresponding
budget. Report the first run separately without calling it a controlled
cold-cache measurement. Doubling 100 to 200 resources should take no more than
3x the median command time for each scenario; also inspect operation counts
to distinguish fixed overhead and filesystem noise from structural growth.
The complete 176-file fixture must finish apply, unchanged reapply and
recovery successfully. Missing or blocked resources cannot be omitted merely
to improve timing.

If M5a demonstrates that a budget is unsuitable for the recorded reference
environment, explicitly revise this plan with measured evidence before closure.
Do not silently relax targets, remove durability or report only a relative
speedup while everyday commands still take minutes.

## Safety and completion gates

- Validate manifest edits, source/target replacement, symlink and hardlink
  aliases, parent rebinding, stale no-op resources and cross-resource overlap
  against the optimized paths.
- Inject failures before intent publication, around target replacement and
  after replacement but before journal publication, as well as fsync and
  journal-CAS failures. Test process interruption during preflight and commit.
- Preserve honest known-changed, unknown and not-attempted outcomes. Verify
  surviving records remain readable and recovery cannot mislabel an incomplete
  batch as complete. Recovery stays read-only.
- Keep secrets and content evidence out of outputs, caches and journals;
  use fake providers for fault tests. Retain existing v1-v6 compatibility.
- Run the relevant regression suite and [maintenance gates](../maintenance.md)
  against the final implementation and installed artifact. Capture profiling
  deltas as well as wall time; a microbenchmark alone cannot close M5.

No roots, profile layer, new format adapter, automatic replay/rollback or
weaker concurrency guarantee is included. Human progress reporting can be
added only as a separately reviewed compatibility-safe aid; it cannot satisfy
the latency gate. Update [status](../status.md) with a link to closure evidence
only after these gates pass.

## Closure evidence — 2026-09-22

### Implementation

M5 shipped without a manifest, journal, CLI, or JSON version change. The
implementation:

- replaced pairwise resource relationship checks with indexed deterministic
  conflict candidates;
- revalidated the planned manifest by captured byte digest instead of
  reparsing the same unchanged manifest before every write;
- indexed journal event-path lookup and retained immutable serialized record
  snapshots for CAS publication;
- published the complete preflight state once, batched contiguous no-op
  transitions without moving unprocessed resources, and kept changed-resource
  intent/commit publications in stable order; and
- added six interruption/fault rows plus a parent-rebinding
  `concurrent_change` regression and a three-probe real-project ablation.

The trusted transition fast path is internal to the executor. Public record
construction, parsing, and ordinary transition APIs still perform complete
schema and event-history validation. No recovery command writes, no secret
content enters records, and no rollback or second ledger was introduced.

### Benchmark evidence

The sanitized fixture contains 1, 10, 30, 100, 176, and 200 public v5
resources with a small symbolic/template mix. Each final row has five
subprocess samples, excludes fixture setup from the timed interval, includes
CLI startup, preflight, journal publication, target durability and
verification, and uses a durable workspace scratch directory rather than
tmpfs. The installed wheel was run from an isolated Python 3.13.15
environment with no source checkout on `PYTHONPATH`.

### Interruption and ablation evidence

`tests/test_m5_interruption.py` adds seven focused rows. They cover failure
before the first writer, after one committed target, after replacement before
journal publication, initial journal publication failure, journal CAS
conflict, an unprocessed no-op, and parent rebinding. The rows assert target
bytes, durable journal state, in-memory error context, and read-only recovery
views together. The parent-rebinding row verifies that the underlying writer
uses `concurrent_change` while the executor reports the outer
`execution_failed` boundary without a changed target.

`experiments/m5_ablation.py` runs real temporary projects with guards on and
off. It reproduces the unsafe stale-plan mutation, last-writer-wins journal
overwrite, and premature no-op confirmation when the corresponding guard is
removed. All guard-on probes pass and every guard-off probe reproduces its
counterexample.
