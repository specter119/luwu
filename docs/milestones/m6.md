# M6: First Usable Bidirectional Pilot

Status: technical acceptance completed on 2026-10-14 after M5 revalidation;
ready for user trial, with trial feedback pending. This record owns the bounded
pilot scope and handoff gates;
the [roadmap](../roadmap.md#next-delivery-sequence) owns sequencing and the
mandatory user-feedback checkpoint before M7-M9 implementation.

The current version 7 implementation has complete bounded acceptance,
installed rehearsal, uncertainty/recovery evidence, and a reviewed trial
handoff. The dated evidence below records technical completion, not a
successful live trial.

## Initial assessment — 2026-10-13

At the start of this review, the partial slice included a sanitized rehearsal in
[`tests/test_m6_rehearsal.py`](../../tests/test_m6_rehearsal.py) and
[`experiments/m6_pilot.py`](../../experiments/m6_pilot.py). It runs both Pi
JSON (`model`, `provider`, `changelog`) and Codex TOML (`model`, `provider`)
fixtures in a normal HOME-shaped layout where source and inputs were contained
under HOME and the target was HOME. The rehearsal covered an absent target with
explicit baseline acceptance and create confirmation, two bidirectional cycles,
preservation of unselected input bytes, post-replace uncertainty, fresh
read-only observation without replay, and an isolated Dotter conflict and
return-management state.

The focused M5/M6 tests and the initial full source suite passed. That
metadata-only rehearsal used no real provider, network, HOME, target, or
Dotter configuration. It did not close every acceptance row: a single closure
artifact was still needed for the two-sided conflict and format-specific
deletion/null matrix, followed by review of the user-trial handoff. The generic
field names also needed replacement with the intended application shapes.

## Review and repair plan — 2026-10-13

Independent Lody sessions using Astra medium reviewed verifiability,
consent/ownership/semantic drift, and filesystem/confidentiality boundaries.
The initial 381-test source suite passed, but adversarial probes exposed
replacement-time authorization gaps, temporary-entry and parent rebinding,
permission changes, lost partial-write outcomes, incorrect deletion/null
verification, invalid TOML acceptance, and sensitive-key spelling bypasses.
The existing rehearsal also used generic field names rather than the names
in the intended application templates. These findings prevented closure.

The resulting repair was split into independent Luna max sessions for the
v7 mutation path, bounded format validation, the application-shaped acceptance
and handoff fixture, and installed benchmark evidence. The parent session
owns integration and final review. No production configuration or Dotter
declaration is part of this work.

Quick design ablations retained the existing span patcher: it preserved
unselected bytes without a new adapter. Standard-library TOML validation
rejected three malformed forms accepted by the original scalar parser. Typed
JSON template serialization preserved null while quoted interpolation did
not; presence-aware verification correctly recognized a completed deletion.
The existing M5 stale-plan, journal-CAS, and no-op-ordering ablations reproduced
their counterexamples when guards were removed. The plan therefore adds no
general format framework, transaction engine, second ledger, automatic replay,
or new manifest version.

## Technical acceptance evidence — 2026-10-14

The [retained acceptance artifact](m6-acceptance-2026-10-14.json) contains
source hashes, installed import provenance, 12 acceptance tests and 28 named
subtests, all 72 M6 test methods, design ablations, and the installed rehearsal.
Source, isolated wheel, and isolated sdist suites each passed 437 tests with
no skips. All 20 installed modules matched the working source bytes. The
installed suites contained no `src/`; every imported Luwu module came from
the selected environment's `site-packages`.

The independent byte oracle replaced the former same-function patch oracle.
A deliberately corrupted unselected input proves that the oracle and runner
assertion detect the error. Additional regressions cover forged declarations,
replacement-time and post-write authority changes, staged-entry and parent
substitution, permission changes, partial multi-input success, verification
exceptions, strict scalar semantics, and sensitive-name spelling variants.

The Dotter rehearsal changes a synthetic declaration and target link, hands
the target to Luwu, returns it to Dotter, and observes that Luwu is blocked
again. No application or real Dotter is invoked. Both complete
[trial-guide scripts](../../tests/fixtures/m6/README.md) were executed with the
installed CLI. Admission, permissions, and return procedures remain in
[maintenance](../maintenance.md#m6-isolated-rehearsal-and-dotter-handoff).

The first installed-suite location under `/tmp` correctly failed fake-rbw
executable-ancestry checks. The unchanged suite passed from private scratch;
no safety check was relaxed. See [local checks](../maintenance.md#local-checks).
The public contract was also corrected to distinguish supplied in-memory
apply/reverse plans from baseline acceptance and CLI confirmation, which
recalculate within each confirming call. No cross-process receipt was added.

Real application loading, real Dotter handoff, provider use, and user-trial
feedback remain unrun. This evidence does not authorize live deployment or
start M7-M9.

## Outcome

Deliver a small Linux pilot that the user can actually try on selected Pi and
Codex public configuration. Demonstrate the complete loop:

declared global/local inputs and template -> reviewed deployment -> application
change -> ownership and conflict observation -> selected reverse-sync preview
-> explicit confirmation -> input update -> recalculation -> safe redeployment.

Use real template and application configuration shapes with sanitized test
values. A reduced literal-JSON model or disconnected forward and reverse
commands cannot close this milestone. This is a bounded trial, not replacement
of all Dotter packages or the whole existing reverse-sync script.

## Required scope

- Explicit source/target roots supporting the normal repository and HOME
  layout, with a small target allowlist and no implicit expansion of authority.
- Declared public machine-local inputs stored outside tracked shared templates,
  with explicit provenance and source/live ownership. Implement only the
  overlay behavior needed by the pilot, not a general profile/package system.
- Public JSON and a bounded TOML subset sufficient for the selected Pi and
  Codex fields. Reverse sync updates declared inputs; it never copies the
  live configuration into a template or rewrites unrelated source bytes.
- Connect field ownership, baseline comparison, selected input mutation and
  forward execution. A v4 observation followed by an unrelated v5 whole-file
  overwrite is not this integration.
- Explicit reviewed transfer from Dotter for the selected targets. Provide
  parent-directory and permission prerequisites, detect conflicting links and
  prevent both tools from deploying the same target.

The implemented pilot uses additive manifest version `7` and the existing
`inspect`, `plan`, `apply`, `accept`, and `reverse-sync` command names. The
public schema is owned by [reference](../reference.md); the mechanism is
described in [design](../design.md). This delivery extends the existing
version 7 contract without changing versions `1` through `6`.

## Acceptance cases

The first required fields are Pi model/provider/changelog and Codex
model/provider. Project trust, hook trust, JSONC, broad format support and
package expansion remain candidates for feedback-driven follow-up.

For both application shapes, demonstrate:

1. Fresh deployment from the real template/input arrangement into isolated
   HOME, with a clean subsequent observation and no-op redeployment.
1. An application-side field change observed as the correct reverse candidate;
   preview changes nothing, confirmation patches only selected declared inputs,
   verification recalculates, and redeployment retains that choice.
1. A source-owned change applied in the forward direction without overwriting
   unrelated live-owned state.
1. A two-sided conflict, stale baseline/input and wrong-owner change stopped
   before a write, with enough explanation for a user decision.
1. An unrelated new live key either preserved under an explicit supported
   policy or producing an actionable review stop. Never delete it from the
   fixture merely to claim a successful round trip.
1. Comments, absent versus null values where the format supports them,
   field deletion, unsupported syntax and unrelated local input content
   handled without silent normalization, adoption or data loss.
1. Interruption or post-write verification failure reported honestly, with
   a tested next inspection/recovery step and no automatic replay.

Retain M5 budgets and safety regressions. Changes to paths or journaling must
not reintroduce the original batch scaling problem.

## Confidentiality and trial boundaries

The pilot covers public values only. Existing configuration containing secrets
cannot be treated as public just because the selected fields are public.
Classify the complete read/write flow before allowing a real target; use an
isolated application profile or leave the target with its current manager
when the public boundary cannot be established. Do not strip credentials from
a production file to force it into the pilot. Real provider integration belongs
to M8, and secret-bearing input persistence remains prohibited.

Keep unsupported packages, generated enterprise provider configuration and
service reloads on their existing explicit workflow. No real configuration is
adopted or deployed merely because isolated tests passed.

## User handoff and feedback checkpoint

Deliver:

- an installable artifact and a repeatable isolated rehearsal using the same
  configuration shapes as the intended trial;
- a small example with normal repository/local-input/target layout and exact
  inspect, plan, confirm, reverse-sync and recovery instructions;
- an allowlist, exclusions and a per-target Dotter handoff procedure, including
  permission prerequisites and a manual way to return management;
- a short known-limitations list, including unsupported syntax, sensitive
  targets and the treatment of undeclared changes;
- a feedback checklist: setup friction, latency, clarity of ownership/conflict
  explanations, preservation of application changes, recovery and missing
  high-value fields. Ask for redacted metadata, not live configuration dumps.

Technical acceptance makes M6 ready for user trial; it does not prove that the
trial succeeded. Record technical completion in [status](../status.md), then
wait for the user's trial results. Review those results and revise M7-M9 scope
before starting their implementation. This checkpoint is explicitly requested
by the user, not an automatic approval requirement inferred from a skill.
