# M6: First Usable Bidirectional Pilot

Status: planned; starts after M5 acceptance. No new capability is implemented
by this document. This record owns the bounded pilot scope and handoff gates;
the [roadmap](../roadmap.md#next-delivery-sequence) owns sequencing and the
mandatory user-feedback checkpoint before M7-M9 implementation.

## Outcome

Deliver a small Linux pilot that the user can actually try on selected Pi and
Codex public configuration. Demonstrate the complete loop:

declared global/local inputs and template -> reviewed deployment -> application
change -> ownership and conflict observation -> selected reverse-sync preview
-> explicit confirmation -> input update -> recalculation -> safe redeployment.

Use real template and application configuration shapes with sanitized test
values. A reduced literal-JSON model or disconnected forward and reverse
commands cannot close this milestone. This is a bounded trial, not replacement
of all Dotter packages or the whole existing reverse-sync script.

## Required scope

- Explicit source/target roots supporting the normal repository and HOME
  layout, with a small target allowlist and no implicit expansion of authority.
- Declared public machine-local inputs stored outside tracked shared templates,
  with explicit provenance and source/live ownership. Implement only the
  overlay behavior needed by the pilot, not a general profile/package system.
- Public JSON and a bounded TOML subset sufficient for the selected Pi and
  Codex fields. Reverse sync updates declared inputs; it never copies the
  live configuration into a template or rewrites unrelated source bytes.
- Connect field ownership, baseline comparison, selected input mutation and
  forward execution. A v4 observation followed by an unrelated v5 whole-file
  overwrite is not this integration.
- Explicit reviewed transfer from Dotter for the selected targets. Provide
  parent-directory and permission prerequisites, detect conflicting links and
  prevent both tools from deploying the same target.

Define public schema/version compatibility in [reference](../reference.md)
and the mechanism in [design](../design.md) before changing execution behavior.
The milestone does not preassign a new manifest version or command syntax.

## Acceptance cases

The first required fields are Pi model/provider/changelog and Codex
model/provider. Project trust, hook trust, JSONC, broad format support and
package expansion remain candidates for feedback-driven follow-up.

For both application shapes, demonstrate:

1. Fresh deployment from the real template/input arrangement into isolated
   HOME, with a clean subsequent observation and no-op redeployment.
1. An application-side field change observed as the correct reverse candidate;
   preview changes nothing, confirmation patches only selected declared inputs,
   verification recalculates, and redeployment retains that choice.
1. A source-owned change applied in the forward direction without overwriting
   unrelated live-owned state.
1. A two-sided conflict, stale baseline/input and wrong-owner change stopped
   before a write, with enough explanation for a user decision.
1. An unrelated new live key either preserved under an explicit supported
   policy or producing an actionable review stop. Never delete it from the
   fixture merely to claim a successful round trip.
1. Comments, absent versus null values where the format supports them,
   field deletion, unsupported syntax and unrelated local input content
   handled without silent normalization, adoption or data loss.
1. Interruption or post-write verification failure reported honestly, with
   a tested next inspection/recovery step and no automatic replay.

Retain M5 budgets and safety regressions. Changes to paths or journaling must
not reintroduce the original batch scaling problem.

## Confidentiality and trial boundaries

The pilot covers public values only. Existing configuration containing secrets
cannot be treated as public just because the selected fields are public.
Classify the complete read/write flow before allowing a real target; use an
isolated application profile or leave the target with its current manager
when the public boundary cannot be established. Do not strip credentials from
a production file to force it into the pilot. Real provider integration belongs
to M8, and secret-bearing input persistence remains prohibited.

Keep unsupported packages, generated enterprise provider configuration and
service reloads on their existing explicit workflow. No real configuration is
adopted or deployed merely because isolated tests passed.

## User handoff and feedback checkpoint

Deliver:

- an installable artifact and a repeatable isolated rehearsal using the same
  configuration shapes as the intended trial;
- a small example with normal repository/local-input/target layout and exact
  inspect, plan, confirm, reverse-sync and recovery instructions;
- an allowlist, exclusions and a per-target Dotter handoff procedure, including
  permission prerequisites and a manual way to return management;
- a short known-limitations list, including unsupported syntax, sensitive
  targets and the treatment of undeclared changes;
- a feedback checklist: setup friction, latency, clarity of ownership/conflict
  explanations, preservation of application changes, recovery and missing
  high-value fields. Ask for redacted metadata, not live configuration dumps.

Technical acceptance makes M6 ready for user trial; it does not prove that the
trial succeeded. Record technical completion in [status](../status.md), then
wait for the user's trial results. Review those results and revise M7-M9 scope
before starting their implementation. This checkpoint is explicitly requested
by the user, not an automatic approval requirement inferred from a skill.
